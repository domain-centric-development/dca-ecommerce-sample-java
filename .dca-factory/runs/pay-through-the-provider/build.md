# Build — pay-through-the-provider

Done in this session. The profile names `carrier.build: dca-modelling`, but the story adds no domain
type, so its modelling craft had nothing to decide, and the stage followed its own description.
The guard `carrier.guard: dca-discipline` was applied to every file written:

- The domain is untouched.
- `application/shared/` still holds only the port and its result.
- The new adapter implements the port and keeps the provider's wire types private to itself.
- The provider call stays outside the transaction.
- The page adapter catches the two named failures, not a base type.

`dca-knowledge` was not asked. Every pattern question (where the ACL sits, one type per outcome)
was already settled in the plan with the node it cites, and the build met no new one.

## Criteria
- authorized-payment-moves-to-review: met.
  - With the suite's stub answering `201`, the shop sends exactly one `POST /payments` whose amount
    and currency are the session total.
  - The session records the reference and moves to the review step.
  - The review page exposes the total under `review-total` (`ProviderPaymentE2ETest`, green).
- refused-payment-stays-at-payment: met. A `402` becomes `REFUSED`, then
  `PaymentInitiationFailedException`. The page shows "The payment was refused. Please choose another
  way to pay." and the session stays at the payment step (`ProviderPaymentIntegrationTest`, green).
- slow-provider-counts-as-unavailable: met. The 2-second read timeout turns the 5-second answer
  into `UNAVAILABLE`, then `PaymentProviderUnavailableException`. The page shows "The payment
  provider is not available right now. Please try again later." (green). A `500` and a dropped
  connection end in the same message (the two extra tests, green).

## Deviations from the plan
- `CheckoutPaymentConfiguration` (checkout `infrastructure/`): the plan did not name it. The
  project has no configuration-properties scan, so the new properties record needs one registering
  class. It follows the `JwtProperties` / `SecurityConfiguration` pair.
- The HTTP client is pinned to HTTP/1.1. The plan did not name this. The JDK client's default h2c
  upgrade got `RST_STREAM` from the WireMock provider on the bodiless `402`. That turned the refusal
  into an unavailable provider, and the refused test failed. The contract needs nothing beyond
  HTTP/1.1.
- The plan's working names (`RestPaymentProvider`, `PaymentProviderProperties`,
  `checkout.payment-provider.base-url`, provider id `provider`, display name "Payment provider") are
  kept, so the tests needed no change.
- For the document stage: `PaymentInitiationFailedException`'s JavaDoc still says the customer sees
  the provider's reason. The page no longer shows that reason; the exception still carries it. The
  plan already flags the matching glossary entry. The build left the JavaDoc as it is because the
  plan did not name the type as changed.
