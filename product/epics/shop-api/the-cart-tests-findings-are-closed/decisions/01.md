# May this task reshape two existing tests as their findings rows prescribe?

## Question

The task closes findings rows whose fix is a change to an existing test. The gate counts both as tests that
"no longer expect what they did" and needs a human's backing, because the task has no `## Changed expectations`.
No expected value or behaviour changes in either:

- `src/test-e2e/java/dev/domaincentric/sample/ecommerce/e2e/ShoppingCartApiE2ETest.java` (closes
  a-malformed-product-id-is-a-bad-request#1, an-unknown-product-in-the-body-is-unprocessable#2,
  an-unusable-cart-request-is-a-problem-document#1): today every refusal test repeats the problem media-type check
  and the still-empty check inline (old `:83-85`, `:91-94`, four copies each); after, they call the helpers
  `assertProblemDocument` and `assertCartStillEmpty`, which hold the same assertions once. Every test still
  asserts the same status, title, detail and empty cart.
- `src/test-integration/java/dev/domaincentric/sample/ecommerce/cart/RemoveCartItemIntegrationTest.java` (closes
  remove-a-line-from-the-cart#3): `aRemoveNamingNoLineOfTheCartChangesNothing` is renamed
  `aRemoveWithAMalformedLineIdChangesNothing` after its scenario (the spec's `Test:` line follows), and
  `removeFormOf`'s `assertThat(form).isNotNull()` becomes `orElseThrow(() -> new AssertionError(...))` — a
  missing form still fails the test.

## Options
- a: Accept both reshaped tests as backed by the findings rows the task closes.
  The plan's `## Changed tests` cites this record; the build already made the change and runs again.
- b: Keep `RemoveCartItemIntegrationTest` as it is and accept only the API test's helpers.
  Row remove-a-line-from-the-cart#3 is then set `wont-fix` or moved out of `closes:`.
- c: Keep both tests as they are.
  The four rows on them are taken out of `closes:` and stay open.

## Recommendation
a — each row's own fix is exactly this change, every assertion is still made, and the tests stay red against a broken shop.
