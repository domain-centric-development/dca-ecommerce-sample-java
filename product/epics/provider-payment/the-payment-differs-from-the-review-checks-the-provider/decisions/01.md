# May the one test that names the failure inside `assertThrows` follow its new name?

## Question
The story renames `AuthorizedAmountDiffersFromReviewException` to `PaymentDiffersFromReviewException` and says "a test
that existed before it stays as it is". One test names the type as the argument of `assertThrows`, so the rename
changes the line that carries its assertion. A task's build gate refuses a changed existing test (`tests-kept`), and the
story has no `## Changed expectations` to back it. What the test asserts — the refusal of another amount, the session
unchanged, no event — stays word for word; only the type's name follows.

Evidence read:
- `src/test/java/dev/domaincentric/sample/ecommerce/checkout/domain/model/CheckoutSessionConfirmAuthorizedAmountTest.java:42`
- the story: "becomes" — one type, so no alias of the old name may remain
- the sibling task the-order-changed-since-the-review-has-the-shared-name asks the same for four tests
  (its record 01, unanswered); its build gate refused with `tests-kept` twice

## Options
- a: The test follows the type's name inside `assertThrows`; what it asserts stays as it is (changes a test's line,
  not its claim). The plan lists it under `## Files` citing this record.
- b: Keep `AuthorizedAmountDiffersFromReviewException` as a deprecated subclass of the new type so the test stays byte
  for byte. Leaves the old word in the code and two types where the story names one.
- c: Change the story so it names the test that follows the name under a `## Changed expectations` section, and
  plan again.

## Recommendation
a — the rename is half the story's content, and a test that names a type can follow its name without asserting
anything new; answering this and the sibling's record alike keeps both rename tasks on one rule.
