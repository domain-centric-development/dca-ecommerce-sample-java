# The happy path already holds here — which scenario carries the story's happy path?

## Question

`a-changed-quantity-is-not-named-a-price-change` is the story's only `(happy path)`, and it holds on today's code —
the story's Notes say so and mean to adopt it. The plan stage may not adopt the only happy path while another
scenario remains (the plan gate refuses a split that leaves the story without its happy path), and the test gate
refuses a green test, so an end-user test of it cannot be seen red. Only
`a-withdrawn-way-to-pay-opens-the-payment-step` changes code. How should the story stand?

Evidence:
- Starting the checkout again supersedes the open session and starts a new one:
  `src/main/java/dev/domaincentric/sample/ecommerce/checkout/application/session/startcheckout/StartCheckoutUseCase.java:135`.
- "Place Order" confirms the active session with the fingerprint of the review it was sent from:
  `src/main/java/dev/domaincentric/sample/ecommerce/checkout/adapter/incoming/web/checkoutcompletion/ConfirmationPageController.java:112`.
- A changed order with no price change is named "Your order has changed since you reviewed it…":
  `src/main/java/dev/domaincentric/sample/ecommerce/checkout/adapter/incoming/web/checkoutcompletion/CheckoutStepPage.java:119`.
- The translation is shown today by
  `dev.domaincentric.sample.ecommerce.checkout.OrderChangedSinceTheReviewIntegrationTest#placeOrderAfterAChangeInAnotherTabIsRefused`
  (spec `ordering`, `place-order-after-a-change-in-another-tab-is-refused`, a shipping change); no test walks the
  quantity change.
- The withdrawn way to pay goes back to the review today: `CheckoutStepPage.java:130` redirects to the step it met.

## Options
- a: Mark `a-withdrawn-way-to-pay-opens-the-payment-step` as the happy path and adopt the changed quantity.
  The plan then adopts `a-changed-quantity-is-not-named-a-price-change` into `checkout-refusals-say-what-happened-holds`
  with `OrderChangedSinceTheReviewIntegrationTest#placeOrderAfterAChangeInAnotherTabIsRefused`. The happy path needs an
  end-user test where the shop withdraws "Mock Payment (Test)" between the payment step and "Place Order"; the shop
  under the browser suite has no way to withdraw a provider today, so the e2e test would need one (a test-only switch
  in the shop under test).
- b: Take `a-changed-quantity-is-not-named-a-price-change` out of this story into an adopted story of its own, and
  mark the withdrawn way to pay the happy path, tested integrated as the Notes intend.
  It costs the story's happy path an `integration` level instead of `e2e`, which the plan stage cannot choose itself.
- c: Keep the story as it is and build an end-user test of the changed quantity.
  The test is green before any code, so the test gate refuses it; nothing delivers.

## Recommendation
a — it keeps one happy path with an end-user test, adopts what holds as the Notes intend, and the withdrawal can be
arranged in the shop under test the way other e2e tests arrange a provider; if a test-only switch is unwanted, b.
