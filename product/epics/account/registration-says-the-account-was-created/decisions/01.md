# How may a story's new browser test pass SharedScenariosTest before its scenario is in product/spec?

## Question
`SharedScenariosTest#everyBrowserTestIsAScenarioOfThisShopsSpecification`
(`src/test/java/dev/domaincentric/sample/ecommerce/specification/SharedScenariosTest.java:97`, added in 7e3b7de)
refuses every browser test whose display name is not a scenario title in `product/spec/**/scenarios.md`. The happy-path
test this story must write — `RegistrationE2ETest#theHomePageARegistrationLeadsToSaysTheAccountWasCreated`, titled
"Registration says the account was created" as the test gate requires — has no scenario there yet: `product/spec` is
written only by the gate that delivers the story. So the build gate's `test` suite is red on that one case, and every
later story with a happy path will be red the same way. Everything else is green: the two mapped tests, the
architecture suite and the formatter.

## Options
- a) `SharedScenariosTest` also accepts the scenario titles of stories under `product/epics/**/story.md` that are
  not delivered yet. That changes one existing test, by hand, outside this story; the story then builds as it is.
- b) Add the title to `TITLED_AFTER_THE_SHARED_SPECIFICATION` in this story. Wrong by that list's meaning, and it
  turns red again at delivery ("a title that becomes a scenario's fails until it is taken off").
- c) Let the pipeline merge the story's scenarios into `product/spec` in the story's worktree before the build gate
  runs the suite (a change to the dca-factory gate, not to this sample).

## Recommendation
a) — the smallest fix, and it holds for every story still in flight; c) is the cleaner fix if the pipeline is meant to
keep `product/spec` and the e2e titles consistent itself. Once one of them is in place, the build runs again unchanged.

## Answer
answer: SharedScenariosTest also knows the titles of the stories not yet delivered (their `####` criteria, title = Title line else the key in words); the spec stays the only source for the Test-line and duplicate checks. Fixed on main in d5ce1e9; nothing changes in this story — run the stage again as it is.
