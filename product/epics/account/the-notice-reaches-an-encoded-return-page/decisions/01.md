# The fragment scenario already holds on today's code — adopt it, or take it out?

## Question
`the-notice-reaches-a-return-page-with-a-fragment` cannot get a red test. Its test,
`RegistrationNoticeIntegrationTest#theNoticeReachesAReturnPageWhoseAddressCarriesAFragment`
(`src/test-integration/java/dev/domaincentric/sample/ecommerce/account/RegistrationNoticeIntegrationTest.java`),
passes before any production code: the registration redirects to `/products#top`, Spring binds the flash map to the
path `/products` (the fragment is no part of it), and the catalogue the browser then asks for — without the fragment —
shows "Account created successfully! Welcome!". The assumption the story answered ("a fragment loses the notice the
same way") does not hold. The happy path is red as expected:
`RegistrationE2ETest#theNoticeReachesAReturnPageWhoseAddressCarriesAnEncodedCharacter` fails on
`expected: <[Account created successfully! Welcome!]> but was: <[]>` — the flash map keeps the query decoded
(`clean code`) and compares it with the request's raw query (`clean%20code`).
No delivered story carries the fragment scenario; only code does, and now this test shows it.

## Options
- a: Adopt the fragment scenario with the test above; the rest of the story runs as planned.
  The plan names it under `## Adopt`, the scenario moves into an adopted story `the-notice-reaches-an-encoded-return-page-holds`,
  and this story keeps its happy path.
- b: Take the fragment scenario out of the story; the encoded address is all it asks for.
  The person removes the scenario and its assumption from story.md; the test written for it is deleted.
- c: Keep the scenario and let its test stand green without a red proof.
  Not possible: the test gate refuses a test that is green before the code.

## Recommendation
a — the behaviour is real and now has a test that guards it; adopting it records that it holds without building anything for it.
