# Opening the review would change the checkout on a GET, which DCA-HEX-014 refuses — allow an exception, or keep the GET a read?

## Question

The story says opening the review takes today's prices into the checkout, and Place Order then orders at them. The
build does this in `GET /checkout/review`: `ReviewPageController.showReviewPage` calls a new command use case,
`RepriceCheckoutInputPort` (`src/main/java/dev/domaincentric/sample/ecommerce/checkout/adapter/incoming/web/checkoutcompletion/ReviewPageController.java`).
Every story test passes with that change. The architecture suite refuses it, though: **DCA-HEX-014** — "GET handlers
must not drive an input port that takes a command … Fix: map the handler to POST, PUT or DELETE, or let the GET
handler ask a query". The rule is enforced and has no exception in this project (`ArchitectureRulesTest` excludes
nothing). The story's note expected this ("a step page's GET then changes an existing session … the plan names it
where that exception is recorded"), but the plan recorded no exception, and switching a rule off is an ADR decision,
not a build stage's.

## Options

- a: Record a documented exception for the review page only.
  In `ArchitectureRulesTest.additionalSelection()`, `ignoringViolationsMatching("DCA-HEX-014", ".*ReviewPageController.showReviewPage.*")`,
  plus an ADR on why the review GET may reprice: it is idempotent for the same prices, and a crawler or prefetch
  only refreshes the guest's own prices. The code stays as built. Cost: the first exception to a hexagonal rule in
  the reference sample, and the .NET shop needs the same exception.
- b: Keep the GET a read and order at the prices the review showed.
  A query shows today's prices without storing them. The review form posts the unit prices it showed, and Place
  Order takes each one only when it equals the checkout's captured price or today's price (a price that is neither
  refuses the order, so a tampered price is never taken). No rule exception. Cost: a third design for the same
  story, and a price that changes twice between showing and pressing refuses the order.
- c: Turn opening the review into a POST.
  "Continue to Review" and every link to the review post to an address that reprices and then redirects to the GET
  page. Reloading the GET then shows the stored prices, not today's, so `the-review-opened-again-shows-todays-price`
  holds only when the guest comes back through the button. That changes what the story asks for.

## Recommendation

a — it is what the story describes, every test already passes, and the exception is narrow: one handler, the
guest's own session, no money moves. It is the decision the story's note anticipated; it only needs an ADR and the
same exception in the .NET shop.

## Answer
answer: correction: none of a/b/c — the review's GET stays a read and shows today's prices; "Place Order" carries a fingerprint of everything the review showed (lines with product, quantity and unit price, buyer details, delivery address, shipping method and price, payment method, total) and works out the same at that moment; a different result refuses the order and the review shows today's. No DCA-HEX-014 exception; what was built to store prices on the GET goes. The story is rewritten accordingly (2026-10-21).
