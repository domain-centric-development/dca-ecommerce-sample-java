# May this task change two existing tests' assertion statements to close the header findings?

## Question

Two of the findings this task closes cannot be fixed without changing an assertion statement in a test that existed
before the story. The tests-kept check refuses that unless a person backs it (file-contracts, "Tests that existed
before the story"). Nothing the tests check changes:

- `src/test-integration/java/dev/domaincentric/sample/ecommerce/backoffice/BackofficeHeaderIntegrationTest.java:64-73`
  (the-back-office-header-is-the-operators#3): the operator-login assertion's chain carries `"admin"`/`"admin"`.
  Naming them (`BackofficeSecurityProperties.DEVELOPMENT_USERNAME`/`DEVELOPMENT_PASSWORD`) changes that statement's
  literals. The login still has to land on `/backoffice/events`. Extracting `registerAndLogInShopper` and
  `logInOperator` (#1) keeps every assertion word for word.
- `src/test-e2e/java/dev/domaincentric/sample/ecommerce/e2e/BackofficeHeaderE2ETest.java:33`
  (the-back-office-header-is-the-operators#2): `assertEquals("Logout", header.logoutButton())` becomes
  `…logoutButtonText()`. The gate does not count that as a rename because
  `src/test-e2e/java/dev/domaincentric/sample/ecommerce/e2e/pages/SiteHeader.java:89` still declares a
  `logoutButton()` of its own.

## Options
- a: Back both test changes as the findings describe them; the plan cites this record in `## Changed tests`.
- b: Back the integration test change; rename the shop's `SiteHeader.logoutButton()` to `logoutButtonText()`
    too (and its caller `LoginE2ETest.java:38`), so both page objects use one name and the gate sees the rename
    on its own.
- c: Close the-back-office-header-is-the-operators#2 and #3 as `wont-fix`; the task closes the other three rows
    and changes no existing assertion.

## Recommendation
b — the two page objects then name the same thing alike. Only the integration test's login literals need a
person's backing; the expected values do not change.
