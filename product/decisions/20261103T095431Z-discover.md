# Agents browse and buy: which problem, for whom, which protocol, measured how?

## Question
The discovery `agent-commerce` (product/discovery/agent-commerce/discovery.md) started from "I want agent to browse
and buy in the shop. Maybe be via UCP." The files settle what the shop does today — an assistant reads the catalogue
over MCP (product/adapter/incoming/mcp/ProductCatalogMcpToolProvider.java), the cart is on the REST API, the
checkout only on the web pages — but not the questions below. Each comes from the discovery's catalogue, word for
word, with the answer the files suggest:

1. What problem should go away, and for whom? Describe it without the solution — what happens today, how often, and
   what it costs. Suggested: a person who hands their shopping to an agent cannot buy here; the agent can only name
   products. No evidence beyond that the shop shows the architecture.
2. Who has the problem — which actors, how many, in which situation? Suggested: the AI assistant, acting for a
   shopper with an account (the existing token), not for a guest.
3. What shows that the problem exists — interviews, tickets, support numbers, observations? Hand them over: a path,
   pasted text, or files in the topic's `originals/` folder. Suggested: none — a demonstration of agent commerce
   over DCA ports.
4. When the problem is solved for someone, which fact would the system record? If you can measure it, from what to
   what should it change? Suggested: `CheckoutConfirmed` for a checkout an agent completed, without a target.
5. What is out of bounds — time, budget, technology, rules a solution must not break? Suggested: no real payment and
   no stored payment data (product/overview.md); the protocol stays in an adapter; the .NET twin follows.
6. Who answers questions about this domain while the work is built? Suggested: `shop-owner`, as for the catalogue
   for assistants.

The protocol choice is the one an option below decides; answer 1–6 in words where the suggestion does not hold.
No web search was available in this run, so the report treats UCP and ACP facts as unverified assumptions.

## Options
- a: UCP checkout over the existing MCP server, for a shopper with an account, payment ending at the stand-in or the configured provider; suggestions 1–6 as written. Matches the wish; the costliest — a protocol session over the five checkout steps, built twice
- b: Own MCP tools for cart and checkout onto the existing use cases, no standard protocol; suggestions 1–6 as written. Smallest; no outside agent recognises it
- c: UCP over its REST binding with a published profile, a surface beside the API; suggestions 1–6 as written. Standard without MCP; a second protocol edge
- d: ACP instead of UCP; suggestions 1–6 as written. The other market standard; same cost as a
- e: The agent browses and fills the cart over MCP, then hands the person a link to the review page; the person confirms. Keeps payment with the person; the agent does not buy alone, so the outcome is `CartItemAddedToCart` from an agent rather than `CheckoutConfirmed`

## Recommendation
a — it is what was asked for, the shop already has the MCP server and the checkout use cases it needs, and a
standard protocol is what makes the sample worth reading for agent commerce; verify the UCP specification first,
and take b as the step before it if the protocol's session shape does not fit the checkout's steps.
